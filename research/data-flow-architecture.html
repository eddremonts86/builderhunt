Architecture · Internal documentation

How BuilderHunt imports, scrapes, and decides what becomes a builder profile.

Three ingestion paths share one safety envelope: a live federated search across 15 sources, an async discovery worker warming a semantic index every 15 minutes, and a policy-gated enrichment pipeline that re-validates a builder's public identity. The diagram below maps every moving piece — from the route that takes a query, to the connector that hits GitHub, to the row that lands in Postgres.

00System overview

Three independent pipelines write into one shared database. Each runs on its own trigger, has its own rate budget, and its own policy gate. The live search is synchronous and request-scoped; the workers are async and batch-oriented.

The three independent ingestion paths

Path 1 — Live search
User types a query → /api/queries or /api/search → orchestrator searchBuilders() fans out to the 15 source connectors in parallel → results are normalized to RawBuilder and returned. No data is persisted from this path beyond analytics.
Path 2 — Discovery worker
Cron every 15 min walks the curated DISCOVERY_MATRIX (30 topics × 4 source groups) → for each cell, runs searchBuilders() → write-throughs kind === 'person' results into builder_embeddings as stubs (no full payload). Pure infrastructure, no LLM calls.
Path 3 — Enrichment worker
User triggers "Refresh public evidence" on a tracked builder → enrichment_jobs row is enqueued → worker claims it under a lease → for each allowed connector, safeFetch() retrieves the public record → resolver deterministically scores it → evidence is persisted with retention (30d raw, 180d accepted).

0115 source connectors · one shape

Every source implements the same contract: input {keywords, sources, perPage} → output RawBuilder[]. The shape is defined in src/lib/sources/types.ts and the comment on BuilderKind is unusually explicit about the failure mode this prevents:

/**
 * organization was added after 30 of 60 GitHub results
 * turned out to be repositories and one of the "people" was a
 * company account. A recruiter searching for people must not
 * be shown either, and merging either into a canonical human
 * is not a subtle error.
 */
export type BuilderKind = 'person' | 'repo' | 'organization'

Triggered by a recruiter in the dashboard. Synchronous. Per request: one orchestrator call, N parallel connector calls, normalize, rank, return.

Key implementation details

Per-source politeness
Each connector has its own rate limit and token usage. GitHub uses api.github.com/search/users with type:user qualifier + hydration via /users/{login} (one call per result — the search endpoint sends no display name, bio, or location, only login + avatar + html_url).
HN uses Algolia, not Firebase
HN's Firebase API has no full-text search; the connector uses hn.algolia.com/api/v1/search with tags=(story,comment) and aggregates hits by author (count, best title, recency, top points). The raw HTML in bios/comments is stripped to plain text.
No data persisted on this path
Live search is read-only. The only writes it triggers are analytics events. To make a builder "tracked," the user must explicitly add it to a list, which is what creates the row in organization_builders and seeds the enrichment job queue.
Failure isolation
A connector that throws or returns [] is logged and skipped — never aborts the search. Users see the sources that responded, never the ones that didn't.

The matrix

Built deterministically from 30 curated topics × 4 source groups. Each topic produces two cells (adjacent source groups, rotated per topic index) so no topic repeats a group and every group is exercised roughly evenly across the matrix.

GroupSourcesWhy grouped
codegithub · gitlab · codebergCode-hosting platforms
communityhn · reddit · lobstersAggregator discussion
contentdevto · stackoverflowLong-form + Q&A
registriesnpm · huggingfacePackage / model releases

Pacing math (per spec)

≤ 4 sources per cell, sequential across cells (never parallel across cells), capped at DISCOVERY_DAILY_STUB_CAP stubs per day. The cursor in discovery_state wraps modulo matrix length; an unknown key resets to 0. The Redis stub counter has a 2-day TTL (covers clock skew) and falls back to an in-memory map when Redis is not configured.

04Path 3 · Public profile enrichment

The most carefully bounded pipeline. Triggered when a member of an organization hits "Refresh public evidence" on a tracked builder. Claims a job, runs the allowlisted connectors, fetches with the full safety envelope, scores with a deterministic resolver, and persists the evidence.

Production status (spec §0). Code-complete-dark as of 2026-07-20: phases 0–6 are implemented, but ENRICHMENT_ENABLED=false in every environment. The 7-day canary, RLS fixture tests, and legal-copy sign-off remain explicit gaps. The spec is in plans/phase-1/42-stealth-scraping/spec.md; the directory name stealth-scraping is legacy — product copy must use Public Profile Enrichment.

The resolver — deterministic, versioned, no LLM

Every evidence candidate is scored against the target. The score is a sum of basis points (max 10 000) over independent signals:

SignalPointsTrigger
verified_owner_cross_link10000Profile owner submitted the URL
exact_stable_source_id10000Candidate's source ID matches the target's source ID
exact_username_reciprocal_link9500Same username AND a reciprocal link exists
exact_username4000Same username, no reciprocal link yet
exact_full_name2500Normalized display name matches
organization_agreement2000Self-declared org matches known org
location_agreement1000Normalized location matches
topic_overlap0–1000Jaccard ratio × 1000
accept_threshold
≥ 9 000 bps + ≥ 2 match signals (or verified_owner flag alone)
review_threshold
≥ 7 000 bps and below accept
name_and_org_mismatch_cap
If both disagree, total bps capped at 6 900 regardless of other signals
forced_reject
conflicting_stable_source_id or verified_owner_rejected always wins
resolver_version
1 — persisted with each evidence row so scoring can be re-run deterministically

Retry & retention

Deterministic backoff
5 min → 30 min → 2 h on rate_limited or upstream_unavailable. After ENRICHMENT_MAX_ATTEMPTS the job is marked failed.
Lease
Each claimed job holds a lease (ENRICHMENT_LEASE_SECONDS). If the worker crashes, reclaimExpiredEnrichmentLeases hands the job to the next run.
Retention pass
After every batch, rows older than ENRICHMENT_RAW_RETENTION_DAYS (30d) for raw evidence, and ENRICHMENT_ACCEPTED_RETENTION_DAYS (180d) for accepted evidence, are deleted in batches of 500.
Subject restriction cascade
If a builder's processing is restricted, every active job for that identity is cancelled and all evidence is purged across every organization — not just the requesting one.

safeFetch envelope (network.ts)

Every outbound request from a connector must go through safeFetch(). The test registry.test.ts enforces this with a static scan: any connector source that calls fetch directly fails the test. The full envelope:

LayerWhat it enforcesWhy
URL validationHTTPS only, public IP only, no credentials in URL SSRF: prevents the worker from being turned into a proxy to internal network or metadata endpoints
Host allowlistallowedHosts per source policy, with subdomain match Defence in depth — even if URL validation passes, the host must be pre-declared
Redirectsmax 3 hops, host revalidated on every hop Prevents redirect-based SSRF (fetch A → 302 → B where B is internal)
Timeout10 sWorker stays bounded
Byte cap2 MBPrevents memory exhaustion; also keeps payloads sane
Content-type allowlistjson · html · plain (+ opt-in extras per call) Refuses binary responses; the Jobindex RSS adapter opts in to application/rss+xml per call
Charset fallbackDeclared header wins, else per-call fallback Legacy feeds declare ISO-8859-1 in prolog; decoding as UTF-8 corrupts Danish characters permanently

robots.txt — fail-closed with three distinct outcomes

The comment on RobotsDecision is unusually explicit about a subtle bug that was fixed:

/**
 * unavailable used to mean two different things, and the
 * difference matters. RFC 9309 §2.3.1.3 is explicit: a 4xx on
 * /robots.txt means the crawler may access any resource.
 * Collapsing that into the same value as a timeout forced every
 * caller to choose between refusing most of the public web and
 * ignoring genuine failures.
 */

OutcomeMeaningConnector behavior
allowedSite answered 2xx, path passes UA-specific rules Proceed with fetch
no_robots_fileSite answered 4xx — RFC 9309 says: permission Proceed (conservative callers can still refuse)
disallowedUA-specific rule matched a Disallow Refuse fetch
unavailableTimeout, 5xx, or other real failure Refuse fetch (fail-closed)

What the spec forbids outright

Hard prohibitions (spec §3). No CAPTCHA solving · no Playwright/Patchright/Selenium · no WARP/Tor/residential proxying · no session-cookie import · no Google dorking · no scraping of search result pages · no LinkedIn/X/Facebook/Instagram automated retrieval · no automatic outreach · no protected-attribute inference · no global sharing of organization-local match decisions.

08Operations · how each worker is invoked

Workers are not started by the app at boot. They are triggered by an external scheduler (typically the platform's HTTP cron) hitting admin endpoints. Each admin route is a thin handler that imports the worker function and returns its result as JSON.
