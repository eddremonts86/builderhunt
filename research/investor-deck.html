01One-sentence thesis

The credential that matters in software is proof of active work — and the credential that matters for hiring is the ability to find that proof fast. BuilderHunt is the infrastructure layer that turns public developer activity into the new résumé.

"Resumes lie. Git history doesn't. And right now, no one is indexing the latter well enough for the way teams actually hire." — The BuilderHunt insight

Every executive who has hired a senior engineer in the last five years has the same story: a keyword-perfect résumé that interviewed well and underperformed on day one. The opposite story is rarer but more diagnostic — the uncredentialed contributor whose commits, comments, and answer velocity made them obviously worth a conversation. We built the search engine for the second story.

02The market pain is old, large, and unsolved

Developer hiring is a $30B+/year global market and the incumbent tools (LinkedIn Recruiter, Indeed, Glassdoor) all share the same model: keyword search over static self-reported profiles. That model has not improved in a decade and was designed for a different world — one where careers were linear and open-source activity was an afterthought.

Three structural problems with status-quo sourcing

Keyword, not behavior

Boolean search on LinkedIn finds words on résumés, not people who actually write Rust in production. The signal recruiters want — recent shipping activity — is invisible to the dominant tools.

Fragmented evidence

The people worth finding don't live on one platform. A senior Rust maintainer is on GitHub. A domain expert answers on Stack Overflow. A rising voice is on DEV.to. Manually cross-referencing five tabs per candidate doesn't scale past the third search.

No real-time signal

When a new maintainer of a popular library starts looking, there's no notification. Hiring is reactive; the best candidates are gone in 72 hours.

The tools that come closest — LinkedIn Recruiter at $170/mo per seat and SeekOut at enterprise pricing — solve the keyword problem at scale but are structurally unable to solve the behavior problem. They index résumés, not git logs.

What "evidence" means in our model

Every result is a RawBuilder with a normalized shape. The shape is designed around one hard rule that we discovered the expensive way and then documented in the type itself:

/**

04The moat: six things competitors can't copy quickly

1. 15 source connectors

Each connector handles its own rate limit, auth model, and data shape quirks (HN needs Algolia because Firebase has no full-text search; GitHub needs hydration because the search endpoint sends no display name). Six months of focused engineering, not a weekend.

2. Identity resolution

Cross-source identity is the hardest problem. We use a deterministic, versioned resolver that scores 7+ match signals and rejects matches with both a name and an organization disagreement — not an LLM, by design, so the audit log is reproducible.

3. Compliance posture

Compile-time policy register, runtime allowlist intersection, hard-blocked list of LinkedIn/X/FB/IG with reasons. Robots.txt cache that distinguishes "absent" from "unavailable" per RFC 9309. This is rare in our category and de-risks enterprise sales.

4. Multi-tenancy from day one

Row-level security on every tenant-scoped table. Organization-scoped search history, builder lists, evidence, notes. A single shared codebase serves thousands of customers with strict data isolation — the table is enforced at the database layer, not the application layer.

5. Spec-driven development

Every feature ships behind a versioned spec.md + task.md + implementation_plan.md trio. The same pattern is used across 50+ completed phases. Investors and acquirers can read the spec to understand intent, not just the code to understand behavior.

6. Inbound product pull

Public roadmap with user voting. Public changelog. Public status page. Public discussion of tradeoffs. The same transparency that makes the product credible with technical users makes the company legible to technical buyers — and to acquirers.

Unit economics we can defend

Because we are API-mediated on every source, our marginal cost per search is dominated by third-party API quota — not compute. With aggressive caching (5-min Redis TTL on results, 24h on enrichment, deterministic backoff to keep us inside every source's rate limit), a Pro customer at $19/mo costs us cents to serve. The interesting economic question is not whether the unit works, it's how fast we can convert free users to Pro once the saved-search workflow demonstrates value — and our phase plans treat that as the primary growth lever.

06Technical bar: the code is the pitch

Most pre-seed pitch decks end here with a logo wall. Ours doesn't, because the technical depth is itself the differentiator. Three things investors should look at:

1. The data ingestion pipeline is policy-gated, not ToS-violating

Every outbound request from a connector goes through safeFetch(), a hardened HTTP client that enforces HTTPS-only, public-IP-only DNS resolution, host allowlists, redirect revalidation, 10-second timeouts, a 2-MB body cap, and a content-type allowlist. A static test in the registry fails any connector that calls fetch directly. The robots.txt cache distinguishes absent from unavailable per RFC 9309, with a comment in the code that documents the exact bug this distinction fixed.

2. The policy register is a hard gate, not a wish list

LinkedIn, X, Facebook, and Instagram are defined as policies with status: 'blocked' and a link to the relevant provider ToS in permissionReference. The runtime allowlist can only narrow the compile-time enabled set; it cannot re-enable a blocked connector. This is the "fail-closed guarantee" and it's unit-tested.

SOURCE_POLICIES = {
  github: { status: 'enabled', acquisitionMode: 'official_api', … },
  linkedin: { status: 'blocked', permissionReference: 'https://www.linkedin.com/legal/crawling-terms — no permission on file' },
}

08Vision: from search to workflow

Search is the wedge. The company is the workflow. The roadmap is already in the product, and three of the next four moves are obvious:

AI sourcing sprints

An agent that takes a hiring brief and returns a shortlist with evidence, citations, and outreach drafts — in 10 minutes, not 10 hours. The compliance posture means the agent can be honest about what it knows vs. what it's inferring.

Outreach with consent built in

Drafts the first message, hosts the reply, and stays inside GDPR's legitimate-interest lane. The same policy gate that protects data acquisition protects outreach — every sent message has an audit row.

Team collaboration

Shared lists, handoffs, interviewer notes, calendar scheduling, and interview intelligence — the workflow that turns a search result into a hire. The Team tier is built for this and the data model already supports it.

Adjacent verticals

The same data plumbing indexes designers (Dribbble, Behance), researchers (arXiv, ORCID), ML practitioners (Hugging Face, Papers With Code), and security researchers. The first vertical is hiring; the second is co-founder matching; the third is grants and funding.

Why now

Three timing vectors converge in 2026:

  1. AI is making credentials less reliable. A self-reported "expert in LLM orchestration" is now harder to verify than ever. Proof of recent shipping activity is the only signal that scales.
  2. Open source is the new résumé. A developer who maintains a popular library has more signal than a CV. The companies that figure out how to discover them first will hire the next decade's senior engineers.
  3. Regulators are closing the gray zones. AI Act, GDPR enforcement, and the death of consumer-grade public-data APIs (LinkedIn, Glassdoor, Indeed all closed read access) make a compliance-first data platform a permanent moat, not a temporary one.
