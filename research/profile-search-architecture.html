Architecture · How scraping becomes search

15 sources, 4 ingestion paths, one shape.

BuilderHunt has four ways data lands in the product: live federated search, the discovery worker that warms the semantic index, the enrichment worker that re-validates public identity, and the new self-managed profile path for people without a public footprint. The connection that isn't obvious is the one piece that holds all four together: every path produces the same RawBuilder shape, and every search consumes that same shape. This document makes that bridge visible.

01The shape is the contract

The reason 15 sources, 4 paths, and one search bar can cohere is that every producer and every consumer agrees on a single shape. The shape is defined in src/lib/sources/types.ts and the comment on the type documents exactly the kind of bug it prevents:

/**
 * What a search result actually is.
 *
 * organization was added after 30 of 60 GitHub results turned out
 * to be repositories and one of the "people" was a company account. A
 * recruiter searching for people must not be shown either, and merging
 * either into a canonical human is not a subtle error.
 */
export type BuilderKind = 'person' | 'repo' | 'organization'

export interface RawBuilder {
  id: string
  kind: BuilderKind
  source: SourceName
  sourceId: string
  username: string
  displayName?: string
  avatarUrl?: string
  bio?: string
  profileUrl: string
  followersCount?: number
  language?: string
  country?: string
  topics: string[]
  metadata: Record<string, unknown>
}

The shape is small on purpose. It carries what a recruiter needs to decide "is this person worth a click" — name, avatar, bio, profile URL, country, topics — and nothing more. Every source-specific quirk lives in metadata as untyped key-value pairs. Adding a new source never requires changing the search pipeline, the dedup, or the renderer.

Why the discriminator is kind, not isPerson

A boolean would seem simpler. It's not. The original code had only kind: 'person' and the search returned 30 repositories when recruiters asked for "react developers". The lesson: the absence of a discriminator is itself a bug. The third value, 'organization', exists because GitHub returns companies in user-search responses, and the search endpoint's own type field is the only authoritative signal (the type:user query qualifier does not exclude organizations).

The shape is the bridge. If a producer can output RawBuilder, the rest of the system — search, dedup, scoring, render, alerts, recommendations, solutions — accepts the result with zero changes. That is the property that makes the four paths composable.

03Path 1 · Live federated search

The path most users experience directly. A recruiter types a query. Within seconds, 15 connectors fire in parallel. Each returns its own slice of RawBuilder (or nothing, if the source failed or the user disabled it). The orchestrator merges and ranks the union. Nothing is persisted on this path.

What each connector is responsible for

Each connector accepts the same input and returns the same shape. It is free to make however many HTTP calls it needs, transform the response however it wants, and stuff anything extra into metadata. The orchestrator does not know or care that GitHub's search endpoint returns no display name and that the connector makes a second call to /users/{login} to hydrate it.

// github.ts — every connector's contract
export async function searchGitHub(
  keywords: string[],

): Promise<RawBuilder[]> {

  // return RawBuilder[] with kind: 'person' or 'organization'
}

What the orchestrator is responsible for

The orchestrator is the only place that knows there are 15 sources. Its job is to run them in parallel, isolate failures, dedupe results, score them by recency, and return a ranked list. It does not parse source-specific data. The connectors are the only place where source-specific data lives.

Per-connector budget
CONNECTOR_TIMEOUT_MS = 8000 in src/lib/search.ts. A hanging source never hangs the search.
Failure isolation
Per-connector try/catch. A broken GitHub response returns [] with a SourceStatus; the search continues with 14 healthy sources.
Rate limiting
The HTTP layer (rateLimit('search-builders', ...)) lives in the route, not the connector. Connectors don't know about user-facing rate limits; they only know about third-party API quotas.
Caching
Redis cache on results, 5-minute TTL. The discovery worker (Path 2) is the warm cache; the live search is the cold read-through.

No data is persisted on this path

Live search is read-only. The only writes it triggers are analytics events. The user cannot add a builder to a list from this path — that creates a row in organization_builders and seeds the enrichment job queue (Path 3). The two paths are deliberately decoupled: live search is fast and stateless; enrichment is slow and durable.

04Path 2 · Discovery worker (the index warmer)

Live search has a latency problem: 15 parallel HTTP calls, each subject to third-party rate limits and network jitter. Even with a 5-minute Redis cache, the first time a recruiter searches for "rust webassembly", the result is what upstream APIs returned within the last few seconds. That's the cold-start tax.

The discovery worker pays that tax in advance. Every 15 minutes, it walks a curated matrix of topics × source groups, re-runs the search pipeline, and writes the results to builder_embeddings as stubs. When a real user searches for a topic the worker has already pre-warmed, the index is ready before the request arrives.

How the worker uses Path 1

The discovery worker calls the same searchBuilders() that the live search uses. That is the connection. The worker is not a separate parallel pipeline; it is the same pipeline running on a cron with the cursor advanced and the results persisted instead of returned.

The matrix

The matrix is built deterministically from 30 curated topics × 4 source groups (code, community, content, registries). Each topic produces two cells (adjacent source groups, rotated per topic index) so every topic is exercised across at least two groups and no group starves.

Cells per run
Configurable via DISCOVERY_CELLS_PER_RUN. Default is small (5–10) to stay inside cron time budgets.
Daily stub cap
DISCOVERY_DAILY_STUB_CAP hard-limits how many stubs land in the index per day. Bounds third-party API spend.
Cursor
Wraps modulo matrix length. Unknown key resets to 0. State persisted in discovery_state row.
Failure isolation
A cell that throws is logged and skipped — the run never aborts.

What gets written

The stubs are not full RawBuilder objects. They are denormalized fields optimized for the semantic index: display name, topics, bio, source identity. The full record lives in the third-party source until a user clicks through; the index is just the pre-computed ranking signal.

05Path 3 · Enrichment worker (the re-validator)

Path 1 searches what's currently public. Path 2 pre-warms the index. Path 3 is the re-validator: when a user adds a builder to a list, BuilderHunt commits to keeping that builder's public identity fresh. The enrichment worker is the only path that fetches with a hardened network envelope and a policy gate.

Why this path is its own thing

Live search tolerates "the source didn't answer" because the user can search again in a minute. Enrichment cannot: if a builder was added to a list, the user expects the public identity to stay current. That implies a different network posture (hardened client, robots.txt honored, rate limits respected), a different storage (durable evidence with content hash, retention windows), and a different concurrency model (claim a job under a lease, fail and let another worker pick it up).

What the resolver does

The resolver is a deterministic, versioned scoring function. It compares the fetched evidence against the builder's known identity and assigns a confidence score in basis points (max 10,000). Seven signals: verified-owner cross-link, exact stable source ID, exact username with reciprocal link, exact username alone, exact full name, organization agreement, location agreement, topic overlap. Two thresholds (accept at ≥9,000, review at ≥7,000). The resolver has no LLM; the audit log is reproducible.

What flows back into search

An accepted enrichment record is treated as a fresh RawBuilder with the new data: the builder's bio, displayName, and topics are updated, and the search pipeline re-derives its score from the new evidence. The enrichment path is the only one that mutates what the search returns.

06Path 4 · Self-managed profiles (planned)

A fourth path opens up for people who have no public footprint in any of the 15 sources. A translator (es, en, fr), a designer without a Dribbble, a researcher with publications in non-indexed repositories — they can create a profile from scratch, upload work samples, and become discoverable in BuilderHunt.

The architectural insight is that the new path uses the same shape with a new discriminator value: kind: 'self-managed-person'. The connector that injects these profiles into the search index does not make a network call; it reads from the selfManagedProfiles table directly and emits RawBuilder objects. The search pipeline does not know the difference.

The connection to scraping, restated

Self-managed profiles are not scraping. They are user-submitted. But they enter the same shape, the same dedup, the same scoring, the same render. From the search pipeline's point of view, the new path is just a sixteenth source that happens to read from a local table instead of an HTTP API. The "scraped vs. not scraped" distinction is preserved in the metadata field and rendered as a chip — but the rest of the system doesn't know or care.

07The bridge — what makes the four paths the same system

The connection between scraping and search is not a single piece of code; it is a set of invariants that all four paths uphold. When a new path joins the system, it has to pass each of these gates. When an existing path drifts, the gates fail loudly.

If a producer can output RawBuilder, the rest of the system accepts the result with zero changes. That is the only thing all four paths have in common, and it is the only thing they need.

The five invariants

1. The shape
Every output is a RawBuilder with a valid kind, source, and sourceId. A new path that doesn't emit this shape is not a new path.
2. The dedup key
Every output has a stable (source, sourceId) tuple. This is what makes dedup work across paths and across the live-search and warm-index layers.
3. The recency signal
Every output has a meaningful lastSeen-equivalent (computed from the source's own activity timestamp, the profile's updatedAt, or the enrichment evidence's observedAt). No recency = no ranking.
4. The discriminator
Every output tags itself honestly: kind: 'person' only when the underlying entity is a person, 'self-managed-person' only when user-declared, 'repo' or 'organization' otherwise. Lying about kind is the original bug that motivated the type.
5. The render contract
Every output renders through <BuilderCard variant> with a chip that names the kind. A result without a chip is not a valid result.

What the bridge looks like in code

The bridge is a single, narrow contract. It's enforced in three places:

// 1. The shape (src/lib/sources/types.ts)
export interface RawBuilder { /* ... */ }

// 2. The producer check (src/lib/search.ts)
// searchBuilders() consumes FusedBuilder[], which extends RawBuilder
// with the scoring fields. Anything that produces RawBuilder can plug in.
export type FusedBuilder = RawBuilder & { /* score fields */ }

// 3. The render contract (src/modules/search/components/BuilderCard.tsx)
// Every variant renders a chip; the chip is required by the component,
// not by the call site, so a forgotten chip breaks the build.
type BuilderCardProps = { builder: FusedBuilder; chip: BuilderChip }

The three places are minimal on purpose. The shape is small. The producer check is one type extension. The render contract is one required prop. Anything more would be a hint that the bridge is doing too much.

What breaks the bridge

Three ways the bridge breaks, and what each looks like in production.
  • A source emits a person where it should emit an organization — recruiters see a company in their "react developers" shortlist. This was the original bug.
  • A new path returns kind: 'person' but has no lastSeen — the result scores zero on recency, sinks to the bottom of every list, and looks broken to the user.
  • A self-managed result is rendered without a chip — the user can't tell it apart from a verified builder. The principle of coverage universal fails; the new path degrades into a worse version of the old one.

08How a result reaches the user

The last step of the journey is the one the user actually sees. Every search result, regardless of which path produced it, goes through the same render pipeline. The pipeline is small and honest: it shows what the result is, where it came from, and how confident the system is about it.

What the chip encodes

The chip is not decoration. It is a single piece of metadata that disambiguates four kinds of result with one glance. The visual hierarchy matters: the "verified" badge is green (the only place green is allowed on a builder card); the "Self-managed" chip is secondary; "Repo" and "Organization" are neutral. A user who learns what these chips mean can make a decision in 200 ms.

What the URL encodes

A result with kind: 'person' | 'repo' | 'organization' links to /builders/$builderId (the existing builder route). A result with kind: 'self-managed-person' links to /u/$handle (the new route). The URLs are deliberately disjoint so a single identity cannot pretend to be two different things via URL confusion.

What the search system owes the user

The user is owed three things, regardless of which path produced the result: (1) an honest chip about what kind of entity it is; (2) a link to a real profile that explains the result; (3) the same scoring, dedup, and ranking rules as every other result. If any of those three is missing, the bridge is broken.
