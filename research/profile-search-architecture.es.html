Arquitectura · Cómo el scraping se convierte en búsqueda

15 fuentes, 4 rutas de ingestión, una sola forma.

BuilderHunt tiene cuatro maneras en que el dato entra al producto: la búsqueda federada en vivo, el discovery worker que calienta el índice semántico, el enrichment worker que re-valida la identidad pública, y la nueva ruta de perfiles auto-gestionados para personas sin huella pública. La conexión que no es obvia es la pieza que sostiene las cuatro: cada ruta produce el mismo RawBuilder, y cada búsqueda consume ese mismo RawBuilder. Este documento hace visible ese puente.

01La forma es el contrato

La razón por la que 15 fuentes, 4 rutas y una sola barra de búsqueda pueden funcionar juntas es que cada productor y cada consumidor se ponen de acuerdo en una única forma. La forma está definida en src/lib/sources/types.ts y el comentario sobre el tipo documenta exactamente el tipo de bug que previene:

/**
 * What a search result actually is.
 *
 * organization was added after 30 of 60 GitHub results turned out
 * to be repositories and one of the "people" was a company account. A
 * recruiter searching for people must not be shown either, and merging
 * either into a canonical human is not a subtle error.
 */
export type BuilderKind = 'person' | 'repo' | 'organization'

export interface RawBuilder {
  id: string
  kind: BuilderKind
  source: SourceName
  sourceId: string
  username: string
  displayName?: string
  avatarUrl?: string
  bio?: string
  profileUrl: string
  followersCount?: number
  language?: string
  country?: string
  topics: string[]
  metadata: Record<string, unknown>
}

La forma es pequeña a propósito. Lleva lo que un reclutador necesita para decidir "¿esta persona merece un click?" — nombre, avatar, bio, profile URL, país, temas — y nada más. Cada particularidad específica de la fuente vive en metadata como pares clave-valor sin tipo. Añadir una nueva fuente nunca requiere cambiar el pipeline de búsqueda, el dedup o el render.

Por qué el discriminador es kind, no isPerson

Un booleano parecería más simple. No lo es. El código original solo tenía kind: 'person' y la búsqueda devolvía 30 repositorios cuando un reclutador pedía "desarrolladores de react". La lección: la ausencia de un discriminador es en sí misma un bug. El tercer valor, 'organization', existe porque GitHub devuelve empresas en las respuestas de búsqueda de usuarios, y el propio type de la respuesta de búsqueda es la única señal autoritativa (el qualifier type:user en la query no excluye organizaciones).

La forma es el puente. Si un productor puede emitir RawBuilder, el resto del sistema — búsqueda, dedup, scoring, render, alertas, recomendaciones, solutions — acepta el resultado sin cambios. Esa es la propiedad que hace que las cuatro rutas sean componibles.

03Ruta 1 · Búsqueda federada en vivo

La ruta que la mayoría de los usuarios experimenta directamente. Un reclutador escribe una consulta. En segundos, 15 conectores se disparan en paralelo. Cada uno devuelve su propia rodaja de RawBuilder (o nada, si la fuente falló o el usuario la desactivó). El orquestador une y rankea. Nada se persiste en esta ruta.

De qué es responsable cada conector

Cada conector acepta el mismo input y devuelve la misma forma. Es libre de hacer las llamadas HTTP que necesite, transformar la respuesta como quiera y meter cualquier extra en metadata. El orquestador no sabe (ni le importa) que el endpoint de búsqueda de GitHub no devuelve display name y que el conector hace una segunda llamada a /users/{login} para hidratarlo.

// github.ts — el contrato de cada conector
export async function searchGitHub(
  keywords: string[],
  options: { language?: string; country?: string; token?: string }
): Promise<RawBuilder[]> {
  // hace la búsqueda, hidrata cada resultado,
  // devuelve RawBuilder[] con kind: 'person' u 'organization'
}

De qué es responsable el orquestador

El orquestador es el único sitio que sabe que hay 15 fuentes. Su trabajo es ejecutarlas en paralelo, aislar fallos, deduplicar resultados, puntuarlas por recencia y devolver una lista rankeada. No parsea datos específicos de ninguna fuente. Los conectores son el único lugar donde viven los datos específicos de cada fuente.

Budget por conector
CONNECTOR_TIMEOUT_MS = 8000 en src/lib/search.ts. Una fuente que se cuelga nunca cuelga la búsqueda.
Aislamiento de fallos
try/catch por conector. Una respuesta rota de GitHub devuelve [] con un SourceStatus; la búsqueda sigue con 14 fuentes sanas.
Rate limit
La capa HTTP (rateLimit('search-builders', ...)) vive en la ruta, no en el conector. Los conectores no saben nada de rate limits de cara al usuario; solo conocen las cuotas de las APIs de terceros.
Cache
Cache de Redis sobre los resultados, TTL 5 min. El discovery worker (Ruta 2) es la cache caliente; la búsqueda en vivo es el read-through frío.

En esta ruta no se persiste nada

La búsqueda en vivo es de solo lectura. Los únicos writes que dispara son eventos analíticos. El usuario no puede añadir un builder a una lista desde esta ruta — eso crea una fila en organization_builders y siembra la cola de enrichment (Ruta 3). Las dos rutas están deliberadamente desacopladas: la búsqueda en vivo es rápida y sin estado; el enrichment es lento y durable.

04Ruta 2 · Discovery worker (el que calienta el índice)

La búsqueda en vivo tiene un problema de latencia: 15 llamadas HTTP en paralelo, cada una sujeta a los rate limits de terceros y a la variabilidad de la red. Incluso con cache de Redis de 5 min, la primera vez que un reclutador busca "rust webassembly" el resultado es lo que las APIs upstream devolvieron en los últimos segundos. Es el impuesto de arranque en frío.

El discovery worker paga ese impuesto por adelantado. Cada 15 minutos, recorre una matriz curada de topics × grupos de fuentes, vuelve a ejecutar el pipeline de búsqueda y escribe los resultados a builder_embeddings como stubs. Cuando un usuario real busca un topic que el worker ya pre-calentó, el índice está listo antes de que llegue la request.

Cómo usa el worker la Ruta 1

El discovery worker llama al mismo searchBuilders() que usa la búsqueda en vivo. Esa es la conexión. El worker no es un pipeline paralelo separado; es el mismo pipeline corriendo en cron con el cursor avanzando y los resultados persistidos en vez de devueltos.

La matriz

La matriz se construye de forma determinística a partir de 30 topics curados × 4 grupos de fuentes (code, community, content, registries). Cada topic produce dos celdas (grupos de fuentes adyacentes, rotados por índice del topic) para que cada topic se ejercite en al menos dos grupos y ningún grupo quede sin atender.

Celdas por ejecución
Configurable vía DISCOVERY_CELLS_PER_RUN. Por defecto es un número pequeño (5–10) para mantenerse dentro del presupuesto de tiempo del cron.
Cap diario de stubs
DISCOVERY_DAILY_STUB_CAP limita cuántos stubs aterrizan en el índice por día. Acota el gasto en APIs de terceros.
Cursor
Envuelve módulo la longitud de la matriz. Key desconocida resetea a 0. Estado persistido en la fila de discovery_state.
Aislamiento de fallos
Una celda que lanza se loga y se salta — la ejecución nunca aborta.

Qué se escribe

Los stubs no son objetos RawBuilder completos. Son campos desnormalizados optimizados para el índice semántico: display name, topics, bio, identidad de fuente. El registro completo vive en la fuente de terceros hasta que un usuario hace click; el índice es solo la señal de ranking pre-computada.

05Ruta 3 · Enrichment worker (el re-validador)

La Ruta 1 busca lo que es público ahora. La Ruta 2 pre-calienta el índice. La Ruta 3 es la re-validadora: cuando un usuario añade un builder a una lista, BuilderHunt se compromete a mantener la identidad pública de ese builder al día. El enrichment worker es la única ruta que hace fetch con una capa de red endurecida y un policy gate.

Por qué esta ruta es su propia cosa

La búsqueda en vivo tolera que "la fuente no haya respondido" porque el usuario puede buscar otra vez en un minuto. El enrichment no puede: si un builder fue añadido a una lista, el usuario espera que la identidad pública se mantenga al día. Eso implica una postura de red diferente (cliente endurecido, robots.txt respetado, rate limits respetados), un almacenamiento diferente (evidencia durable con content hash, ventanas de retención) y un modelo de concurrencia diferente (reclamar un job bajo lease, fallar y dejar que otro worker lo recoja).

Qué hace el resolver

El resolver es una función de scoring determinística y versionada. Compara la evidencia obtenida contra la identidad conocida del builder y asigna una puntuación de confianza en basis points (máx. 10.000). Siete señales: cross-link del dueño verificado, source ID estable exacto, username exacto con link recíproco, username exacto solo, full name exacto, acuerdo de organización, acuerdo de ubicación, solapamiento de temas. Dos umbrales (accept ≥ 9.000, review ≥ 7.000). El resolver no tiene LLM; el log de auditoría es reproducible.

Qué vuelve a la búsqueda

Un registro de enrichment aceptado se trata como un RawBuilder fresco con los nuevos datos: el bio, el displayName y los topics del builder se actualizan, y el pipeline de búsqueda re-deriva su puntuación a partir de la nueva evidencia. La ruta de enrichment es la única que mutaba lo que la búsqueda devuelve.

06Ruta 4 · Perfiles auto-gestionados (planificada)

Una cuarta ruta se abre para personas que no tienen huella pública en ninguna de las 15 fuentes. Un traductor (es, en, fr), un diseñador sin Dribbble, un investigador con publicaciones en repositorios no indexados — pueden crear un perfil desde cero, subir muestras de trabajo y hacerse descubribles en BuilderHunt.

El insight arquitectónico es que la nueva ruta usa la misma forma con un nuevo valor del discriminador: kind: 'self-managed-person'. El conector que inyecta estos perfiles al índice de búsqueda no hace una llamada de red; lee de la tabla selfManagedProfiles directamente y emite objetos RawBuilder. El pipeline de búsqueda no nota la diferencia.

La conexión con el scraping, replanteada

Los perfiles auto-gestionados no son scraping. Son user-submitted. Pero entran por la misma forma, el mismo dedup, el mismo scoring, el mismo render. Desde el punto de vista del pipeline de búsqueda, la nueva ruta es solo un decimosexto conector que por casualidad lee de una tabla local en vez de una API HTTP. La distinción "scrapeado vs no scrapeado" se preserva en el campo metadata y se renderiza como chip — pero el resto del sistema no lo sabe ni le importa.

07El puente — qué hace que las cuatro rutas sean el mismo sistema

La conexión entre scraping y búsqueda no es una única pieza de código; es un conjunto de invariantes que las cuatro rutas cumplen. Cuando una nueva ruta se une al sistema, tiene que pasar cada uno de estos gates. Cuando una ruta existente se desvía, los gates fallan ruidosamente.

Si un productor puede emitir RawBuilder, el resto del sistema acepta el resultado sin cambios. Eso es lo único que las cuatro rutas tienen en común, y es lo único que necesitan.

Los cinco invariantes

1. La forma
Cada output es un RawBuilder con un kind, source y sourceId válidos. Una nueva ruta que no emita esta forma no es una nueva ruta.
2. La clave de dedup
Cada output tiene una tupla estable (source, sourceId). Esto es lo que hace que el dedup funcione entre rutas y entre la búsqueda en vivo y el índice caliente.
3. La señal de recencia
Cada output tiene un equivalente de lastSeen significativo (computado desde el timestamp de actividad de la fuente, desde updatedAt del perfil, o desde observedAt de la evidencia de enrichment). Sin recencia no hay ranking.
4. El discriminador
Cada output se etiqueta honestamente: kind: 'person' solo cuando la entidad subyacente es una persona, 'self-managed-person' solo cuando es declarada por el usuario, 'repo' u 'organization' en otro caso. Mentir sobre kind es el bug original que motivó el tipo.
5. El contrato de render
Cada output se renderiza a través de <BuilderCard variant> con un chip que nombra el kind. Un resultado sin chip no es un resultado válido.

Cómo se ve el puente en código

El puente es un único contrato, estrecho. Se hace cumplir en tres sitios:

// 1. La forma (src/lib/sources/types.ts)
export interface RawBuilder { /* ... */ }

// 2. La comprobación de productor (src/lib/search.ts)
// searchBuilders() consume FusedBuilder[], que extiende RawBuilder
// con los campos de scoring. Todo lo que produce RawBuilder encaja.
export type FusedBuilder = RawBuilder & { /* score fields */ }

// 3. El contrato de render (src/modules/search/components/BuilderCard.tsx)
// Cada variant renderiza un chip; el chip es obligatorio por el componente,
// no por el call site, así que un chip olvidado rompe el build.
type BuilderCardProps = { builder: FusedBuilder; chip: BuilderChip }

Los tres sitios son mínimos a propósito. La forma es pequeña. La comprobación de productor es una extensión de tipo. El contrato de render es un prop obligatorio. Cualquier cosa más sería una pista de que el puente está haciendo demasiado.

Qué rompe el puente

Tres formas en que el puente se rompe, y cómo se ve cada una en producción.
  • Una fuente emite una persona donde debería emitir una organización — los reclutadores ven una empresa en su shortlist de "desarrolladores de react". Este fue el bug original.
  • Una nueva ruta devuelve kind: 'person' pero no tiene lastSeen — el resultado puntúa cero en recencia, se hunde al final de cada lista y parece roto para el usuario.
  • Un resultado self-managed se renderiza sin chip — el usuario no puede distinguirlo de un builder verificado. El principio de cobertura universal falla; la nueva ruta se degrada en una versión peor de la antigua.

08Cómo llega un resultado al usuario

El último paso del recorrido es el que el usuario realmente ve. Cada resultado de búsqueda, sin importar de qué ruta venga, pasa por el mismo pipeline de render. El pipeline es pequeño y honesto: muestra lo que el resultado es, de dónde viene y cuánta confianza tiene el sistema sobre él.

Qué codifica el chip

El chip no es decoración. Es una única pieza de metadatos que desambigua cuatro tipos de resultado de un vistazo. La jerarquía visual importa: el badge "verified" es verde (el único sitio donde se permite verde en una builder card); el chip "Self-managed" es secundario; "Repo" y "Organization" son neutros. Un usuario que aprende lo que significan estos chips puede decidir en 200 ms.

Qué codifica la URL

Un resultado con kind: 'person' | 'repo' | 'organization' enlaza a /builders/$builderId (la ruta de builder existente). Un resultado con kind: 'self-managed-person' enlaza a /u/$handle (la nueva ruta). Las URLs son deliberadamente disjuntas para que una misma identidad no pueda pretender ser dos cosas distintas por confusión de URL.

Lo que el sistema de búsqueda le debe al usuario

Al usuario se le deben tres cosas, sin importar de qué ruta venga el resultado: (1) un chip honesto sobre qué tipo de entidad es; (2) un enlace a un perfil real que explique el resultado; (3) las mismas reglas de scoring, dedup y ranking que cualquier otro resultado. Si falta alguna de las tres, el puente está roto.
